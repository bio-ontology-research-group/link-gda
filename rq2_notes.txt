RQ2 — handover notes
====================

RQ2 is the phenotype-free claim: the variants -f (functions), -s (expression
sites) and -fs (both), which reconstruct the gene side without the gene's
mouse-ortholog phenotype annotations. This file lists what is settled, what is
open, and the reviewer comments that land on RQ2 specifically.

Read README.md first for how to invoke the models. Read paper/reviews/STATE.md
for why the project was rebuilt.


1. Protocol — match RQ1 exactly
-------------------------------

The reviewer's one endorsement of the results was that "RQ1 and RQ2 are tuned
symmetrically, INDIGENA gets the same grid, and I think those results hold."
That endorsement is worth keeping, so RQ2 must be tuned the same way, not with
inherited hyperparameters:

  - grid: embedding dim {100, 200, 400, 800} x learning rate {1e-3, 1e-4, 1e-5}
    x batch {16384, 32768, 65536, 131072} x projector {owl2vecstar,
    owl2vecstar_gda} = 96 configurations per variant, 288 for the three
  - tune on fold 0, seed 0, selecting on the mean rank of a validation split
    held out from that fold's training diseases; no test fold enters the search
  - --dual_arms --skip_test on every tuning run
  - --tolerance 15, maximum 1000 epochs
  - report both settings, uncalibrated and calibrated, for every variant
  - deterministic average-rank tie handling (already the default)

Then, for each selected configuration: ten folds at seed 0, and seeds 1-9 at
fold 0, without --skip_test so predictions are written.

Learning rates enter filenames as Python renders them, so 1e-05 and not
0.00001. Results carry a by_graph suffix with --use_graph and an inductive
suffix without it. Both cost time to rediscover here.


2. Storage
----------

/ibex/user filled at 1.5 TB during the RQ1 rebuild and 206 runs died instantly
with no output, which looked like a code fault for some time. Keep predictions
for everything -- they are small and every metric is recomputed from them --
and keep checkpoints only where something downstream consumes them. A TransD
checkpoint at dim 800 is 1.5 GB and there is no reason to keep one per fold and
seed unless ConvKB-D will warm-start from it.


3. Reviewer comments that land on RQ2
-------------------------------------

3.1  "Gene function annotations alone" is not function alone   [review 2.3]

     For any gene not already in the graph through its own modality, the
     builder adds exactly one has_phenotype edge (kge_transd.py, the
     gene-phenotype loop: `elif use_phenotypes or gene not in entities`, with
     entities.add(gene) firing immediately after, so it is one edge, chosen by
     CSV row order). The variant therefore is not phenotype-free.

     Measured on the current data:

       variant   candidate genes affected   of 4399 pool   test genes/fold
       -f                              32           0.7%        4.0  (0.6%)
       -s                             297           6.8%       41.0  (6.6%)
       -fs                             16           0.4%        2.0  (0.3%)

     -f and -fs are barely affected; -s is the real exposure. In edge terms the
     contamination is 32 and 16 phenotype edges against roughly 315,000
     function triples, under 0.01% of the graph.

     The reviewer asks for the counts above AND a rerun excluding the affected
     genes. Two routes: drop those genes from the graph entirely, which makes
     "function alone" literally true but shrinks the candidate pool per variant;
     or keep them and report an edge-matched control on the subset of test genes
     that never receive a fallback edge, which keeps the pool fixed. DECISION
     PENDING -- do not design around either until it is settled.

3.2  Candidate-pool comparability                              [follows from 3.1]

     If fallback genes are excluded per variant, -f ranks against 4367
     candidates and -s against 4102 while RQ1 uses 4399, so mean ranks stop
     being comparable across tables. The plan under discussion is a single
     shared pool, excluding the union, with RQ1 recomputed on it. That
     recomputation is free: predictions are saved as full score matrices, so
     restricting the pool is a column mask, not a rerun. DECISION PENDING.

3.3  -f vs -p is confounded by graph size                      [review 2.5]

     Functions contribute 315,631 gene-function edges plus the whole GO
     projection; phenotypes contribute 213,988. So "function substitutes for
     phenotype" may partly be "more edges beat fewer edges". The reviewer's fix
     is an edge-count-matched subsample of the function edges. NOT ADDRESSED.
     Note gene-site is larger still at 536,923 edges, so -s carries the same
     confound more strongly.

3.4  The excluded-genes benchmark caption is wrong             [review 1.2]

     This is the 409 gene-disease pairs whose gene has no MGI-propagated
     phenotype annotation -- tab:excluded in main.tex, evaluated with -f and -fs
     only, because the similarity baselines, Exomiser and INDIGENA return no
     score on those pairs.

     The caption claims "the ten seeds share this split". They do not: the
     train/validation disease split is seeded by --random_seed unless
     --val_seed is passed, and the original runner never passed it. So the
     reported 699.86 +/- 174.11 and 646.87 +/- 91.49 mix data resampling with
     initialisation and negative sampling, and the standard deviations are not
     what the caption says they are.

     The fix is one flag and one rerun. run_excluded_seeds.sh now passes
     --val_seed and --tolerance, so the runner is ready. The reviewer put this
     first in his suggested order of work.

3.5  Emphasis in the paper                                     [review 2.3]

     The Methods admit the fallback edge; the abstract, RQ2 section and
     Conclusion do not. Whatever is decided in 3.1, the claim wording has to
     match it.


4. State of the code
--------------------

Everything needed is on main. The rebuild corrected the evaluator to score
causes_phenotype via predict_hrt (it previously scored the inverse of
associated_with), added per-gene calibration and the two-arm design, made tie
handling deterministic, and chunked the evaluation so large dimensions fit in
ordinary GPU memory. RQ1 is complete: 384 tuning configurations and 285
fold/seed runs.

Not yet done anywhere: RQ2 tuning, the RQ2 tables, the excluded-genes rerun,
and ConvKB-D beyond -pfs.


5. Open questions to resolve before large runs
----------------------------------------------

  - 3.1: exclude fallback genes from the graph, or keep them and report an
    edge-matched control?
  - 3.2: one shared candidate pool across RQ1 and RQ2, or per-variant pools?
  - 3.3: is the edge-count-matched control being run, or is the confound
    acknowledged in the text?
  - is -s reported at all? It carries 6.8% fallback contamination against 0.7%
    and 0.4% for the others, and the largest edge-count confound.

Each of these changes which results are reported rather than which code
produces them, so the runs can be designed now, but the first two should be
settled before the 288 tuning jobs are submitted.
